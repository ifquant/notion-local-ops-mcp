# Notion AI Code Agent：三阶段完善计划

日期：2026-10-15

状态：第一阶段 1A–1E 已实现，A1–A13 本地验收及 G0/A14 真实 Notion 验收通过。适用范围仍为同一存活服务进程内的非交互工作流；测试入口为临时隧道，滚动重载曾出现一次间歇性测试失败，未宣称长期部署或跨重启接管完成。第二阶段 2A 已实现并通过本地及本次约定的真实 Notion MCP 功能验收：包含工作创建重试、双项目隔离、精确 LF 写入、运行中跨对话恢复、五项错误范围拒绝及增量终态读取。按用户确定的边界，Notion 消息发送失败作为外部现象记录，不计为 MCP 缺陷；2B–2E、完整 B13 与第三阶段待实施。详见 [第一阶段验收记录](phase1-verification.zh-CN.md) 和 [2A 验收记录](phase2a-verification.zh-CN.md)。

## 目标

让 Notion AI 通过本地 MCP 服务方便、可靠地完成持续的代码工作：读取项目、分析问题、修改文件、运行验证，并在断线、切换对话或服务重载后恢复进度。

Notion AI 负责分析和决定下一步；MCP 服务负责文件操作、执行任务、保存工作记录和提供结果。Notion 自己完成“读取—分析—修改—验证”是主要验收路径，`delegate_task` 保留为可选能力。

“持续”分为三个层次：

| 层次 | 期望行为 | 对应阶段 |
| --- | --- | --- |
| 持续访问 | 路径准确、读取完整、编辑结果明确 | 第一阶段 |
| 持续推进 | 工作上下文可保存，跨对话找回任务和下一步 | 第二阶段 |
| 持续执行 | 长任务独立运行，接入服务重载后仍可追踪，并支持再次触发分析 | 第三阶段 |

## 当前基础与证据边界

已有文件搜索与读写、补丁编辑、Git 工具、后台命令、任务元数据和日志存储，以及 launchd、隧道维护、滚动重载和 relay 追踪。主入口使用 Streamable HTTP，兼容旧 SSE。

实现前的初步分析发现以下问题；其中第一阶段涉及项的修复状态以验收记录为准：

- 文件工具的相对路径以 `WORKSPACE_ROOT` 为基准，命令/Git 的默认目录可由 `set_default_cwd` 改变；默认目录和 relay 绑定又由所有连接共享。
- 后台命令使用 `communicate()`，执行结束后才保存输出，运行中无法读取增量日志。
- 执行线程和进程控制信息保存在 MCP 进程内，缺少跨重载接管和启动时状态核对。
- 取消已完成任务会改写终态；取消只处理直接子进程，没有完整的进程组管理。
- 文本按字节截断后，续读位置可能跳过尚未返回的内容。
- 缺少工作记录、任务列表和请求去重；任务清理没有按运行状态排除活跃任务。

2026-10-15 的检查中，在隔离依赖环境、排除本机代理干扰后，现有 180 项测试通过。临时目录专项复现确认了运行中日志为空、取消改写成功状态、分页漏读和路径基准不一致等行为。真实 Notion 会话、线上隧道及任务完成后的自动接续尚未验收。

## 第一阶段：让现有工具可靠

### 目标

让一次 Notion coding 会话可以准确访问文件、观察任务进度，并可信地判断执行结果。交付标准是下述接口约定与验收场景成立，不只是新增几个参数或通过原有测试。

### 审查结论与实施原则

原计划的方向成立，但需要先解决五个实施歧义：旧路径行为如何兼容、长行如何续读、日志截断后游标如何解释、取消何时算完成，以及限制资源后如何避免任务卡死。

- 采用增量扩展，保留现有工具名与主要字段；行为纠错和兼容性例外必须写进工具描述与迁移说明。
- 第一阶段的新推荐调用统一显式传入项目 `cwd`；保留旧调用的默认行为，不把全局默认目录误称为独立会话。
- Shell 后台任务与委派任务复用进程管理和日志能力，避免只修 `run_command_stream`。同步 `run_command` 同样需要正确处理超时、输出上限和进程清理。
- 只保证本阶段定义的进程与输出边界；任务跨重启接管、持久化项目隔离仍由后续阶段负责。
- 具体响应字段已在第一阶段实现与测试中固定；实际调用方法见 README，验收证据见第一阶段验收记录。后续阶段的候选接口仍不是已交付能力。

### G0 接入与授权前置检查

将接入可行性检查放到 Notion 验收之前尽早完成，不等所有功能交付后才发现客户端无法使用。G0 不新建工具，也不要求新增鉴权框架，优先验证现有能力。

- 确认目标 Notion 工作区、Agent 入口、测试服务地址和代码版本；在授权的测试连接中完成工具发现、`server_info` 和一次无敏感内容的文件读取。仅有健康检查成功不能证明工具可用。
- 使用独立测试目录和任务状态目录；不对真实项目注入写入失败或进程故障。`cwd`/`WORKSPACE_ROOT` 不是权限边界，测试目录也不是沙箱。若需要限制实际访问范围，应使用受限系统账号或隔离环境；未隔离时必须明确接受服务账号的文件和 Shell 权限。
- 接入非本机客户端前验证实际部署的鉴权：无凭证和错误凭证不能调用工具，有效凭证才能访问；允许公开的发现/健康端点不计作工具授权。密钥不得写入计划、示例或验收截图。新增连接、隧道和权限授予单独确认，不作为计划审查的隐含动作。
- 实测客户端能否连续调用、传递 cursor、读取结构化结果和分次等待；记录观察到的等待行为，不把服务端 30 秒上限当作 Notion 的已知能力。等待不稳定时先用短等待或查询验证，不提前承诺自动持续运行。

G0 未满足时可以继续隔离的本地实现和测试，但不能对外开放未鉴权服务，也不能将第一阶段标记为 Notion 可用。

### 1A：统一显式路径，保留旧调用兼容

为 `list_files`、`search`、`read_text`、`write_file`、`apply_patch` 和项目级 `list_skills` 增加可选 `cwd`，与现有 Shell/Git 的显式 `cwd` 对齐。

| 输入情况 | 第一阶段的解析规则 |
| --- | --- |
| 显式绝对 `cwd` | 使用该目录，先验证存在且为目录 |
| 显式相对 `cwd` | 相对 `WORKSPACE_ROOT` 解析，不受全局默认目录影响 |
| 绝对文件路径 | 保留绝对目标，不再拼接 `cwd` |
| 相对文件路径且显式 `cwd` | 相对本次调用解析出的 `cwd` |
| 文件工具未传 `cwd` | 保留原有 `WORKSPACE_ROOT` 基准 |
| Shell/Git 未传 `cwd` | 保留原有“全局默认目录 → `WORKSPACE_ROOT`”回退 |

- 每次调用入口解析一次目录并固定下来，批量读取、补丁所有文件和移动目标共享该基准，不能执行到一半重新读取全局状态。
- 返回实际 `resolved_cwd` 和目标绝对路径；省略路径的目录查询使用本次基准目录。
- `set_default_cwd` / `get_default_cwd` 的描述明确标注进程级共享作用域。Notion 推荐指令改为每次使用显式 `cwd`，直到第二阶段提供稳定工作标识。
- 不改变绝对路径和符号链接的既有访问范围；`WORKSPACE_ROOT` 仍然是路径锚点，不是沙箱。
- `delegate_task.context_files` 的相对路径按任务实际 `cwd` 解释，传给执行器的上下文路径明确化。

验收重点：两个同名文件项目、相对 `cwd`、绝对路径、批量文件、补丁移动目标、全局目录被另一客户端改变，以及原有省略 `cwd` 的调用。

### 1B：完整且有界的文件读取

- 保留 `start_line` / `line_limit`；明确 200 行是默认值，额外设置硬上限，不能用超大参数绕过预算。内容预算按实际返回文本的 UTF-8 字节数计算，行号前缀也计入。
- 普通分页只在实际已返回的行之后推进 `next_offset`。最后一行只返回了一部分时，不能给出跳到下一行的游标。
- 增加可表示“行内位置”的续读 cursor。遇到超长行时，响应提供 `next_cursor`、部分行标记和实际范围；旧的行游标不足以续读时返回空值和明确提示，不能伪造完整行。
- cursor 绑定目标文件和文件版本标记。继续读取前后核对版本；发现变化返回 `file_changed`，要求重新开始，避免把两个版本的片段混为完整文件。本阶段只用于分页一致性，不提前引入写入版本校验。
- cursor 与手动起始位置同时提供时明确拒绝。空文件、文件结尾、越界位置、无末尾换行和无效 cursor 都有确定结果。
- 批量读取同时限制文件数和总文本预算。未处理文件明确标为 deferred，并返回继续读取所需信息；不能把未读取文件报告成成功或不存在。
- 避免先把整个大文件读入内存再截断输出。UTF-8 跨块字符不被拆坏；对无效编码沿用明确的替换或拒绝策略，并报告发生了替换。

验收重点：按游标拼接后，按接口声明的换行规范化规则与固定测试输入比较，覆盖中文、emoji、超长行和不同换行形式；展示行号不混入源文本拼接比较。保留旧文本展示规则，不把文本分页描述为原始文件的逐字节导出。文件在两次读取间变化必须可识别。

### 1C：增量日志与查询约定

- stdout/stderr 在任务执行期间持续追加到各自日志，两个管道都要及时消费。不能等待换行才处理，也不能只读 stdout 导致 stderr 填满后阻塞。
- `get_task` / `wait_task` 增加可选日志 cursor 和本次输出预算；不传 cursor 时保留有界的 tail 查询行为。每次响应给出下一 cursor、是否还有已保存输出、日志截断标记。
- cursor 绑定任务、输出流和已消费位置；保留每个流内部顺序，不承诺 stdout 与 stderr 之间有精确的全局时序。校验负值、越界及其他任务的 cursor。
- 字节定位与文本解码规则一致，不能因 UTF-8 分块重复或丢失字符。cursor 表示读取位置，不是删除确认；同一 cursor 可重读已保存的相同区间。
- `wait_task` 默认继续等待终态，新增可选“有新输出即返回”模式。等待事件、终态更新和日志写入配合，避免刚有输出却丢失唤醒；取消一次等待只结束该等待，不取消任务。
- 区分 `wait_timed_out` 与 `execution_timed_out`。旧 `timed_out` 字段在兼容期注明其接口相关含义，新客户端以两个明确字段为准；查询不能覆盖持久化的执行超时事实。
- `completed=true` 表示执行收尾和已保留日志的写入已经完成；日志是否被读取到结尾由 `has_more` 独立表示。
- 对已 flush 的测试输出，正常本地环境下应在 1 秒内可查到。子程序自身缓冲、尚未写出的文本不属于 MCP 能即时提供的内容。

验收重点：运行中读取、无换行输出、双流大量输出、UTF-8 分块、多读者 cursor、等候期间输出到达、完成后继续读剩余日志，以及读取成本不随历史日志总量线性增长。

### 1D：明确终态、取消与异常处理

保留 `queued`、`running`、`succeeded`、`failed`、`cancelled` 的基本状态。取消请求通过 `cancel_requested` 等附加信息表达，不能一收到请求就报告任务已停止。

| 情况 | 预期行为 |
| --- | --- |
| 启动前已接受取消 | 不启动子进程，完成必要收尾后进入 `cancelled` |
| 正常退出 | 完成日志收尾后，根据退出码进入 `succeeded` 或 `failed` |
| 运行中取消 | 请求终止，限时等待，必要时升级强制终止；确认受管理进程结束后进入 `cancelled` |
| 执行超时 | 按同样的清理流程结束进程，进入 `failed`，记录 `execution_timed_out=true` |
| 等待超时 | 仅返回 `wait_timed_out=true`，不改任务状态、不终止进程 |
| 终态任务再次取消 | 幂等返回原终态，不能把成功改为取消 |
| 无本进程控制句柄的活动记录 | 返回无法控制的明确结果，不伪报取消成功、不自动重跑 |

- 用同一状态锁/转换入口处理完成、取消和超时竞争。若接受停止请求前已观察到进程退出，保留实际退出结果；否则首个接受的停止原因决定收尾原因，后续请求不得覆盖已确定的结果。为竞争次序编写确定性测试。
- macOS/POSIX 下启动独立进程组，先 TERM、宽限后 KILL，并限时收尾。管理同组后代，包括 shell 已退出但后代仍持有输出管道的情况，不能无限 `communicate()`。
- 超过收尾时限仍无法确认受管理进程结束时，保持非终态及 `completed=false`，附加 `cleanup_failed` 和已接受的停止原因，保留控制信息及占用的执行额度。调用应有界返回错误，不能为了释放容量伪报完成；后续核对确认退出后才能结束任务。
- 本阶段不提供 PTY、交互式 stdin 或后台服务托管。非交互任务关闭 stdin；自行脱离进程组的守护进程不在取消保证内，不能宣称整个任意进程树都已停止。其他平台未有等价验证时明确能力限制。
- Shell 与 delegate 路径统一覆盖命令构造失败、Popen 失败、日志读取/写入失败和超时。委派任务也必须注册完成事件；不能只在 shell 路径支持事件等待。
- 若日志或元数据写入失败，尝试停止受管理进程；保留可查询的内存错误并输出服务诊断。磁盘不可写时不承诺持久化成功，不能把任务报告为正常成功。
- 同步 `run_command` 复用必要的进程控制逻辑并保持调用形式，不自动重跑或静默改成后台提交。输出截断要有标记，超时返回仍为可序列化文本。

验收重点：启动前取消、运行中取消、完成后取消、重复取消、多个等待者、自然退出/取消/超时竞争、命令启动失败、持有管道的后代进程和终止失败后的如实报告。

### 1E：限制资源、保护清理与报告写入失败

- 第一阶段采用本进程的并发准入上限。满额时返回可识别的 `capacity_exceeded`，不启动进程、不积累无界等待线程；同步和后台执行共用预算。滚动重载期间多个进程的全局配额留到独立执行器阶段。
- 日志先采用简单的每任务保留上限：达到上限后继续消费管道，但丢弃后续超额内容并记录截断及丢弃字节数。不暂停读管道，不静默轮转导致旧 cursor 指向其他内容。
- 日志截断后只保证已保留部分可重读，不宣称完整；结构化结果解析同样受大小限制，不能对被截断的数据声称提取了完整结果或通过 schema 验证。
- 终态任务释放进程引用、读线程和完成/取消对象；并发等待者已经取得的事件仍能收到完成信号，后续查询从持久化结果恢复。
- 清理以已确认终态和完成时间为依据。跳过 queued/running、状态未知、元数据损坏及仍在读取的任务，报告跳过原因；旧终态记录缺少完成时间时采用有说明的兼容规则。
- 校验 `task_id` 的合法形式后再组成路径；清理不跟随任务目录符号链接，不删除任务根目录之外的目标。读取、清理和终态落盘之间需要协调；文件缺失或已清理时返回结构化错误。
- 将“写入失败如实报告”提前到第一阶段：捕获文件写入和补丁落盘异常，多文件操作报告已经完成、失败及尚未执行的文件；若失败文件可能已部分写入，标记需重新读取，不能报告零修改或整体成功。原子替换、版本冲突控制及更完整的编辑保护仍在第二阶段。

初始预算建议如下，实施时集中配置，并在响应/`server_info` 中暴露实际限制。测试使用小预算覆盖边界，无须生成巨大日志。

| 项目 | 初始默认值 | 触顶行为 |
| --- | --- | --- |
| 单文件读取 | 默认 200 行，硬上限 2,000 行；文本 32 KiB | 返回准确续读信息 |
| 批量读取 | 最多 16 个文件，总文本 64 KiB | 超文件数拒绝；超文本预算 deferred |
| 单次任务日志读取 | stdout/stderr 合计 32 KiB | 返回 cursor 和 `has_more` |
| 每任务日志保留 | stdout/stderr 合计 16 MiB | 继续排空，明确报告后续丢弃量 |
| 同步命令返回 | stdout/stderr 合计 32 KiB | 保持执行，响应注明截断 |
| 同一服务进程的执行并发 | 4 个 | 明确拒绝新提交，允许稍后重试 |
| 单次 `wait_task` | 默认 30 秒，最大 30 秒 | 超出拒绝并提示分次等待 |
| 终止宽限 | TERM 后 2 秒，再 KILL；收尾最多再等 2 秒 | 超限报告清理失败，不伪报已停止 |

上述文本预算不等于完整 JSON/MCP 消息大小；元数据、路径和错误摘要也需限制长度，避免用巨大的错误文本绕过输出预算。30 秒等待上限只是初始服务策略，实际 Notion 超时预算需在端到端验收时确认。

新增硬上限是有意的兼容性收紧：旧客户端超过行数、批量数或等待时长上限时，返回包含实际限制和重试方式的结构化错误，不静默改变请求含义。数值参数统一拒绝负数及非有限值；零值只在有明确含义的接口接受（例如零秒等待表示立即查询），不能隐式变成无限制。

### 实施切分与涉及文件

### Notion 调用流程与失败处理

第一阶段交付一份短的 Agent 使用说明，而不是新增推理框架：先确认项目及 Git 基线，显式传入 `cwd` 搜索和读取，针对既有文件优先使用 `apply_patch`，修改后回读目标并核对 diff，再运行验证。补丁 dry-run 只证明当时可应用，不是版本锁或事务保证；没有版本写入保护期间，应避免多个写入者同时修改相同文件。

| 返回情况 | Agent 下一步 |
| --- | --- |
| 文件分页或批量 deferred | 沿返回 cursor 续读或处理剩余文件，不能把片段当全文 |
| `file_changed` | 重新读取并分析，不能继续拼接旧内容 |
| `wait_timed_out` | 保留同一 `task_id` 继续等待/查询，不重新提交命令 |
| 提交响应丢失，不知道是否启动 | 标记结果不确定并核对现有记录；第一阶段无提交去重，禁止盲目重试有副作用的命令 |
| `capacity_exceeded` | 稍后重试提交，不进行紧密循环 |
| 部分写入失败 | 回读受影响文件并核对 diff，再制定修复；不重放整份补丁 |
| `cleanup_failed` 或控制权不可用 | 报告未确认停止，停止依赖该任务已结束的后续操作 |
| 终态且 `has_more=true` | 继续读取已保存日志；日志截断时明确证据不完整 |

只有修改内容符合目标且验证实际通过，才能报告本次 coding 工作完成。工具调用成功、命令返回零和所有业务验收通过是不同层次；验证失败要读取原因后决定修复或请求输入，不能无变化重复运行。

### A14 可重复的真实使用验收

使用一个无凭证、无外部网络依赖的小型测试项目，预置一个可由本地测试复现的简单错误。正常流程由 Notion 自己调用文件和命令工具完成，不能用委派给另一个 coding agent 的结果代替。

1. **定位与复现。** Notion 发现工具、确认显式 `cwd`，搜索和读取代码，运行测试并读到预置失败；记录目标文件与失败原因。
2. **修改与核对。** Notion 应用最小补丁，回读修改内容并检查 diff；从本地独立核对目标文件及非目标文件，确认改动没有越出任务范围。
3. **持续观察。** 验证命令先 flush 一个标记，再等待测试端释放，最后输出第二个标记并退出。必须在任务未结束时经 Notion 读到首个标记，再释放测试门闩；不能只凭最终日志推断实时读取成功。
4. **完成与取消。** 读到真实退出状态、剩余日志及修复后测试结果；另起可取消任务，由 Notion 取消，从本地核对受管理进程组退出。终态后重复查询和取消不得篡改结果。

验收证据保存代码版本（脏工作区需包含差异快照）、配置限制、客户端入口、脱敏的工具调用参数与返回、`task_id`、最终 diff 和本地进程核对结果。每一步分别标为通过、失败或未测，并关联证据；既有测试数量不是新增细则通过的依据。测试结束只清理已确认归属本次验收的进程和临时文件，保留验收记录，不自动提交或推送代码。

### 阶段边界

本阶段的可保证路径是“同一存活服务进程内、显式项目目录、非交互任务”。仍不承诺全局默认目录/relay 的跨对话隔离、任务跨重载接管、自动重试、PTY 输入、脱离进程组的守护进程管理，或自动唤醒 Notion。

服务重载后遇到旧活动记录，只报告控制权不可用；不能为看起来完成了恢复而改写成取消或自动重跑。稳定工作标识和恢复记录在第二阶段完成，真正的执行接管在第三阶段完成。

## 第二阶段：支持跨对话恢复工作

### 目标

让 Notion AI 在断线或新对话中找回项目、工作记录和已有任务，核实现场变化后继续推进。主路径仍由 Notion 自己读取、分析、编辑和运行验证，不依赖委派另一个 Agent。

本阶段的“恢复”是恢复上下文和查询已有执行，不是接管进程，更不是重新运行旧命令。以下方案基于第一阶段提交 `441728e`；2A 的实际交付范围见验收记录，其余仍待实施。

### 当前实现与必须补齐的约定

| 当前实现 | 对第二阶段的影响 |
| --- | --- |
| `session.py` 的默认 cwd、relay 绑定是进程级全局变量 | 新调用必须显式关联工作，不能把 MCP 连接或全局默认值当成项目身份 |
| `tasks.py` 已持久化任务 JSON 和日志，锁是实例内 `RLock` | 复用现有结果与日志；新增记录的唯一性和并发更新必须覆盖不同进程 |
| `executors.py` 的控制对象、事件和容量限制在内存里 | 重启后能查记录不等于能控制旧进程；去重不能依赖内存字典或容量锁 |
| `files.py` 的 `file_version` 是用于分页的 stat 信息 | 保留现有分页契约，另定义写入预期版本，不能直接承诺内容级冲突保护 |
| `write_file` 与 `patching.py` 最终直接写目标文件 | 需要共享写入保护；补丁有预检和部分失败报告，但不是多文件事务 |
| `relay_bridge.py` 在事件送出时读取当前全局绑定，失败时清空它 | 必须在调用入口固定归属；旧请求的失败不能清掉后来建立的绑定 |
| `purge_tasks` 删除终态任务目录 | 新增去重与 checkpoint 引用后，清理必须保留可解释的关联和去重凭据 |

滚动重载会出现新旧服务进程短暂并存，因此只验证两个客户端连接同一 Python 进程不够。身份、checkpoint 和提交去重需要双进程验收；活动进程的接管仍留在第三阶段。

### 2A：显式工作身份与最小持久化存储

实现状态：已完成本地及本次约定的真实 Notion MCP 功能验收，见 [2A 验收记录](phase2a-verification.zh-CN.md)。当前 schema 1 只保存 workspace/run/任务关联，后续阶段再增加 checkpoint 与任务提交去重记录。`get_run` 暂只恢复身份、目标与目录可用性；列表属于 2B。按工作路由 relay 在 2E 实现前，带 run 的调用不回落到旧全局绑定。

- `workspace_id` 对应一个规范化的现有项目根目录；同一路径的别名归一，不因相同 Git remote 合并不同 worktree。目录移动、删除或身份变化时报告不可核实，不自动绑定到新目录。
- `run_id` 对应一次开发工作，保存项目、目标、验收条件和创建时间；`task_id` 仍表示一次执行。一个项目可以有多个工作，不新增全局“当前 run”。
- 项目工具增加可选 `run_id`。带 run 的调用默认使用该项目根目录，显式相对 cwd 从根目录解析；cwd 和文件目标超出该项目时返回范围冲突，不悄悄回落到全局默认值。查询/等待/取消任务时从持久化关联确定 run；额外传入的 run 若不匹配则拒绝。
- 不带 run 的旧调用保留现有行为，但不享有跨对话隔离保证。工作身份用于防串项目，不是权限或沙箱；Shell、委派程序及同账号其他程序仍可能访问项目外资源。
- 推荐用 Python 标准库 SQLite 保存新增的 workspace、run、checkpoint、任务关联和去重记录，使用唯一约束和事务更新。SQLite 支持跨连接并发读，但同时只有一个写事务，故必须设置有限锁等待并返回可重试的 `store_busy`，不能无限阻塞。[SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)
- 保留现有任务 JSON 与日志为执行状态/输出的权威来源，不在数据库再复制一套终态。数据库负责身份、关联、checkpoint 和提交凭据；遇到记录不一致时返回明确的不完整状态，不伪造成功。
- 存储带 schema 版本，放在本地 `STATE_DIR`，目录/敏感文件权限沿用 0700/0600。迁移失败、损坏、磁盘满时停止有关写入，不清库重建。旧任务仍可按 ID 查询；列表明确标为未关联，不凭 cwd 猜测属于哪个 run。

### 2B：可核实的 checkpoint 与恢复接口

checkpoint 保存目标进展、关键发现、已改文件、验证证据引用、相关 task_id、下一步和阻塞原因，不保存完整对话、原始密钥或整份日志。服务端采集 Git/文件基线；Agent 提交的“测试通过”等结论单独标为声明，不能覆盖真实任务结果。

- 每次保存需带 `expected_revision`，以事务比较后更新，防止两个对话互相覆盖摘要。冲突返回当前 revision；保存响应丢失后先读取核实，不盲目覆盖。关联任务必须属于同一 run。
- Git 基线包含 HEAD、暂存区和工作区变化、未跟踪文件清单，以及相关文件版本；不能只比较分支名或 HEAD。非 Git 项目仍可用文件基线恢复。
- 恢复返回保存时间、revision、旧基线与当前状态的差异、关联任务状态和 `control_available`。权限不足、目录不存在、扫描超限或文件在采集时变化，标记为未知/不完整，不能归类为“无变化”。基线是有时间范围的观测，不是整个项目的原子快照。
- 只核实 checkpoint 关联文件与有界 Git 摘要，不默认扫描/哈希整个仓库。初始预算建议：单 checkpoint 64 KiB、最多 100 个文件、单文件版本采集 8 MiB、单次合计 32 MiB；超限返回未核实项，不降级成弱版本。输出继续遵守第一阶段的分页和字节限制。
- 列表默认 20 条、最多 100 条，使用稳定排序和绑定过滤条件的游标；只返回摘要，日志复用现有任务查询接口。旧任务目录采用有界扫描，不在首次查询时无界导入。

新增工具限于以下六个候选接口；不另建同义的 restore/resume 工具：

| 接口方向 | 约定 |
| --- | --- |
| `open_workspace(path)` | 登记或返回现有项目身份；不创建项目、不切换全局 cwd |
| `start_run(workspace_id, goal, acceptance_criteria, creation_key)` | 创建工作；同一项目和创建键重试返回原 run，参数不同则冲突 |
| `list_runs(workspace_id, cursor, …)` | run_id 遗失时从项目找回工作 |
| `get_run(run_id, …)` | 返回最新 checkpoint、现场变化和有界任务摘要；只查询，不启动执行 |
| `save_checkpoint(run_id, expected_revision, checkpoint)` | 带版本保存摘要与证据引用 |
| `list_tasks(run_id / workspace_id, status, cursor, …)` | 按明确范围找任务；未关联旧任务需显式查询 |

Notion 指令采用固定接续顺序：打开项目 → 找到/创建 run → 读取 checkpoint 和现场差异 → 查询已有任务 → 决定下一步。阶段性分析、修改和验证后保存 checkpoint；记录过期时先核实受影响结论。

### 2C：持久化提交去重与崩溃窗口

统一在后台命令和委派任务的公共提交入口实现，不给 `run_command_stream` 单独做一套。不带 run 的旧调用保持兼容；带 run 的后台提交要求 `idempotency_key`。同步 `run_command` 不承诺提交去重，需要可恢复的执行统一走后台接口。

- 唯一范围是 `(run_id, idempotency_key)`。指纹包含执行类型、命令/委派输入、规范化 cwd、超时及影响执行的参数。后台命令的两个入口归一到同一类型；忽略仅影响展示的参数。首次提交冻结有效默认值及 `auto` 选择的执行器，重试不能因服务默认值变化产生第二个任务。
- 相同键和相同请求返回原 task_id 及当前状态，包括已失败/取消的任务；不同请求返回参数冲突。确实要重新执行时使用新键，由调用者明确发起。
- 先查已有键，再检查新任务的执行容量；满载时仍可找回已提交任务。新请求验证或容量拒绝不占用去重键。
- 在持久化唯一预留中分配 task_id，初始化现有任务目录，再以一次性启动声明取得启动资格。提交记录包含所属服务实例和阶段；双进程竞争只有一个实例可以启动。不能仅因“不是本进程创建的”就接管预留。
- 数据库提交、任务文件初始化和操作系统启动进程不是一个事务。必须测试预留后、文件初始化后、启动声明后及进程启动后崩溃的窗口。不能确认是否启动时返回原 ID 和 `submission_uncertain`，禁止自动再启动；这保证不因重试重复启动，不保证命令副作用恰好一次。
- 初版对遗留预留保守报告待核实，不实现自动抢占/重放。确认终态、资源释放和查日志继续复用第一阶段能力；控制对象遗失时如实返回不可控制，不把旧 `running` 记录擅自改成成功或取消。
- `purge_tasks` 与提交查询协调：清理后保留最小去重凭据和已清理标记，重复键返回原 ID 与 `task_purged`，不得重新执行；checkpoint 中的引用保留并显示结果已清理。普通任务 GC 不删除去重凭据，完整删除工作及其凭据不纳入本阶段。

### 2D：带版本的编辑保护

保留第一阶段 `file_version` 和分页 cursor，另外由 `read_text` 按需返回 `edit_version`。编辑版本基于同一次稳定读取的原始字节内容及文件身份，不基于带行号文本或换行归一化后的输出。超过采集预算或读取期间发生变化时，不返回可用编辑版本。

- `write_file` 接受 `expected_version`；`apply_patch` 接受按路径列出的 `expected_versions`，覆盖修改、删除以及移动的源和目标。创建使用明确的“不存在”预期，不把缺参数解释为允许覆盖。
- 带 run 的编辑要求预期版本；旧调用仍可不提供，但结果必须说明未做冲突检查。`dry_run` 只预检、不预留版本，正式写入重新验证。
- 所有服务内文件写入共用按规范化路径的跨进程锁，包含旧调用和移动目标；多路径按固定顺序获取，等待有上限。锁内重新核实路径身份、预期版本和预检条件。Shell、Git 命令、委派执行及外部编辑器不参与这套文件锁。
- 更新普通文件采用同目录临时文件再替换，保留权限/可执行位；创建采用不覆盖已存在目标的提交方式。受保护的补丁保留未改部分的换行/BOM，拒绝无法无损解码的输入；符号链接和多硬链接目标先明确拒绝，不悄悄改变链接语义。
- 原子替换只保护单次文件替换，不是版本比较与写入的原子组合。外部编辑器仍可能在最终校验后写入，不能声称彻底消除这类竞争；多文件移动、删除也不构成原子事务。[Python 文件替换说明](https://docs.python.org/3.11/library/os.html#os.replace)
- 补丁先完成全量预检，再顺序提交。失败报告区分已应用、失败、未应用，以及“目标已创建但源删除失败”等实际副作用；不自动回滚，以免覆盖其他程序的新修改。磁盘满、权限变化和替换失败也须保留准确证据。

### 2E：工作范围追踪与兼容收口

- 为调用追踪附加 workspace/run/task 关联，在调用入口捕获不可变的归属和 relay 绑定版本；任务查询从存储反查归属，调用结束时不得重新读取另一个工作当前的全局绑定。
- `bind_relay_run` / 清除操作扩展 run 范围；旧全局绑定只服务于未关联调用，禁止作为 run 调用的回退。TTL 到期或发送失败只清除对应绑定版本，不能清除后来建立的新绑定。
- 本阶段 relay 仍是尽力而为的追踪通道，不是 checkpoint 存储，也不新增后台完成事件。绑定可保持进程内状态；重载后恢复结果明确要求重新绑定，未绑定时不发送到其他工作。令牌不进入 checkpoint、普通日志或返回摘要。
- 区分“工具调用未抛异常”和“业务操作成功”，结构化失败不能被记录为验证通过。状态恢复以任务记录和现场证据为准，不依赖 relay 投递成功。
- 一并更新工具 schema/描述、`server_info` 能力与限额、README、Notion 使用指令及旧数据兼容测试。核心触点是 server/session、任务存储/执行公共入口、files/patching 和 instrument/relay；不重写已验收的日志和进程生命周期实现。

### 交付物

- 2A–2E 的接口约定、最小存储迁移及兼容说明。
- 工作记录恢复、任务查找、持久化提交去重和带版本编辑保护。
- 更新后的 Notion Agent 接续指令，以及分层验收记录。

### 验收标准

| 编号 | 必须证明的行为 |
| --- | --- |
| B1 身份与兼容 | 两客户端交错访问两个项目；全局 cwd 变化不影响带 run 调用；错误范围被拒绝；旧调用仍可用 |
| B2 找回工作 | 创建响应丢失不重复建 run；run_id/task_id 遗失后可按项目分页找回；服务重启后记录仍可读 |
| B3 并发 checkpoint | 两个 OS 进程以同一 revision 保存，只有一个成功；旧摘要不会覆盖新摘要；跨 run 任务引用被拒绝 |
| B4 现场核实 | HEAD 未变但暂存/未暂存/未跟踪文件变化仍被发现；非 Git、项目消失、超限和权限失败分别可解释 |
| B5 提交去重 | 两进程并发重试同一键，实际启动计数为 1；后台入口别名共享去重；委派入口同样覆盖；参数变化报冲突 |
| B6 丢响应与容量 | 提交响应丢失、容量已满及任务终态后重试均找回原任务；新请求容量拒绝不占键 |
| B7 崩溃与重载 | 在各提交持久化/启动边界注入崩溃；重复请求不启动第二份进程；不确定状态和失去控制权明确可见 |
| B8 清理与旧数据 | 查询和 GC 并发不会误判为可重跑；清理后保留去重凭据与 checkpoint 引用；旧任务可读且不错误归属 |
| B9 存储失败 | 数据库锁冲突、迁移失败、损坏及磁盘满均有界失败，不丢旧记录、不误报保存或提交成功 |
| B10 编辑冲突 | 旧版本更新/删除/移动被拒绝；并发创建不覆盖已存在目标；双进程及新旧文件接口共用锁；dry-run 后变化被重新检查 |
| B11 写入语义 | 覆盖权限位、CRLF/BOM、无效编码、链接拒绝、路径变化及替换失败；多文件部分失败与真实磁盘结果一致 |
| B12 relay 竞态 | A 调用未结束时绑定 B，A 结果仍归 A；旧绑定发送失败不清掉新绑定；重载未绑定不串发；摘要无令牌 |
| B13 真实 Notion | 在 if quant’s Space 的两个独立对话中完成下述接续流程，不用委派 Agent 替代 Notion 自己分析 |

B13 使用隔离测试项目：对话 A 建立 run、分析文件、启动可控后台验证并保存 checkpoint；对话 B 通过 run_id 恢复，再补测仅凭项目查找，读取已有任务的增量日志与终态，不重新提交命令。人为改变一个相关文件后，B 能识别旧结论过期，旧版本编辑被拒绝，重新读取后完成修改与验证，再保存新 checkpoint。记录实际工具调用和任务启动次数，不以聊天中的“已完成”代替证据。

单元测试、MCP 双客户端、OS 双进程故障测试和真实 Notion 分别记录结果。第一阶段回归必须继续通过；新增连接、部署或账号权限仍沿用 G0 的单独授权边界。

### 阶段边界

本阶段完成的判定是：跨对话找回事实、核实变化、复用已有任务、避免重试重复启动，并以明确版本编辑文件。MCP 服务重启后可以恢复记录，但不保证旧任务持续存活、恢复取消控制或自动修正所有遗留执行状态。

独立执行器、自动重试、持久化完成事件、自动唤醒 Notion、全仓语义索引、多文件原子事务和多用户权限隔离均不纳入本阶段。去重凭据暂随工作长期保留；达到存储预算时拒绝新建并提示整理，不通过静默淘汰换取再次执行的风险。

## 第三阶段：支持长期执行与再次触发分析

### 目标

让长任务独立于 MCP 接入进程运行，可靠处理重载和异常中断，并验证 Notion 再次运行后的接续闭环。

### 工作范围

1. **分离接入与执行。** 将后台执行器放入独立、受管理的本地进程。MCP 接入层负责提交和查询；执行器负责进程、日志、超时和取消。优先沿用现有本地部署方式，不引入无必要的分布式基础设施。
2. **核对执行状态。** 保存执行所有者、心跳和进程身份。执行器启动时核对非终态任务，对无法确认继续执行的任务标记为中断或待核实，不能无限保持 `running`。
3. **定义恢复与重试规则。** 区分“继续已有进程”和“重新执行命令”。有副作用的命令不因重启而自动重跑；允许重试的步骤需要明确条件、预算和次数上限。
4. **提供持久化事件。** 记录任务完成、失败、中断和需要输入等事件，支持游标读取、确认与去重。通知失败不丢失任务结果，不让执行依赖通知渠道可用。
5. **验证 Notion 接续方式。** 先验证手动再次运行可恢复，再验证 Custom Agent 的定时或事件触发。评估既有 relay 能否承接完成事件，并在真实环境验证触发、关联工作和重复触发处理。
6. **建立有限的推进循环。** 每次恢复后读取新结果，再决定继续修改、重新验证、结束或请求必要输入。设置工作时限、重试预算和停止条件，避免无变化轮询或自触发循环。

### Notion 侧能力边界

Notion 官方文档说明 Custom Agents 可通过定时、Notion/Slack 事件和手动方式触发，并在这些运行中使用 MCP。具体能力及配置以实施时的官方文档与账号实测为准。

- [MCP connections for Custom Agents](https://www.notion.com/help/mcp-connections-for-custom-agents)
- [Custom Agents 与触发配置](https://www.notion.com/help/custom-agents)

本地任务完成是否能够直接唤醒原对话尚未确认，不能作为未经验证的架构前提。若无法自动触发，应明确交付为“后台任务持续运行、状态可恢复、手动或定时接续”，并把自动唤醒列为未完成项。

### 交付物

- 独立执行器及其部署、状态核对和运维说明。
- 持久化任务事件、恢复规则及异常中断处理。
- 经实测的 Notion 接续方案与配置说明。
- 重载、执行器异常、客户端断线和通知失败的故障测试报告。

### 验收标准

- 长任务运行期间重载 MCP 接入服务，任务仍能继续；重连后可读取连续日志和最终结果。
- 执行器异常退出后，任务状态能够被核对，不留下无人管理且永久 `running` 的记录。
- 模拟断线和重复提交，不会重复执行带相同去重键的命令。
- 完成事件可重复读取而不丢失；重复投递不会造成重复启动下一步。
- 通知渠道不可用时，任务仍能正常结束，结果可在后续恢复中找回。
- 在真实 Notion 环境完成“读取代码—修改—启动长验证—离开当前运行—再次触发—恢复结果—完成或继续修复”的闭环。
- 清楚记录该闭环采用手动、定时还是事件触发，以及是否支持返回原对话。

## 实施顺序与完成判定

按第一阶段 → 第二阶段 → 第三阶段推进，每阶段划分成可独立审查的小改动，并先完成该阶段的行为验收，再进入依赖它的下一阶段。

第一阶段顺序：G0 接入条件核对 → 1A 显式路径与兼容 → 1B 完整分页 → 1C/1D 日志与生命周期联合验收 → 1E 清理及写入失败报告收口 → MCP 与 Notion 分层验收；资源预算随对应能力交付，G0 未通过时仅继续本地工作。第二阶段顺序：2A 身份与存储 → 2B checkpoint/查找恢复 → 2C 持久化提交去重 → 2D 编辑冲突保护 → 2E 追踪隔离及兼容收口 → B1–B13 分层验收；每项随实现交付对应故障测试，不把跨进程验证留到最后。第三阶段先完成独立执行器，再接续 Notion 触发链路。

保留现有工具及存储中可复用的部分。暂不把向量数据库、全仓语义索引、大型调度平台或新的 Agent 推理框架作为前置条件；只有实际使用证据表明需要时再评估。

完成报告分别列出代码/测试证据、本地进程证据和真实 Notion 端到端证据。已有测试通过、端点可访问或任务记录落盘，均不能单独证明持续分析闭环已经完成。
